## 一、项目概述

### 1. 项目名称

EasyProject

### 2. 产品定位

EasyProject 是一款开源、简洁、美观的本地优先项目管理工具，帮助个人与小型项目团队通过任务分解、依赖管理和甘特图快速制定、跟踪及复盘项目计划。

### 3. 项目背景

现有项目管理产品常见以下问题：

- 免费版本功能受限，甘特图、导入导出等能力通常需要付费；
- 专业工具学习成本较高，不适合轻量项目和个人使用；
- 部分产品界面复杂，创建和维护计划的操作成本高；
- 云端产品依赖网络，用户难以完全掌控项目数据；
- 开源方案常偏重功能实现，安装、交互和视觉体验不够友好。

EasyProject 首先以“本地可用、数据可控、甘特图好用”为核心形成桌面 MVP，再根据真实用户反馈决定是否扩展 Web、移动端和云同步。

### 4. 产品原则

- **本地优先**：无须注册和联网即可使用核心功能；
- **简单优先**：新用户应能在 10 分钟内建立第一个项目计划；
- **可视化优先**：任务表与甘特图保持同步，减少重复操作；
- **数据可迁移**：支持开放格式导入导出，避免数据锁定；
- **渐进增强**：先完成稳定的单机闭环，再扩展协作和多端能力。

## 二、目标与范围

### 1. MVP 核心目标

1. 用户可以创建项目并管理项目下的任务；
2. 用户可以通过甘特图查看任务时间、层级、依赖和进度；
3. 用户可以在任务表或甘特图中调整计划，二者数据实时一致；
4. 用户可以通过 JSON、CSV、XLSX 与 ICS 迁移项目和日历数据；
5. 应用在 Windows 桌面端离线稳定运行，界面清晰统一；
6. 项目数据存储于用户应用数据目录，并具备备份和恢复能力。

## 三、用户画像与需求

### 1. 核心用户

#### 个人项目负责人

- 管理个人开发、学习、写作或交付项目；
- 希望快速拆解任务、安排时间并观察延期风险；
- 重视免费、本地存储和低学习成本。

#### 小型团队项目成员

- 参与 2–10 人的小型项目；
- 需要清楚知道任务负责人、先后关系和截止时间；
- 希望使用统一视图同步计划，但暂不需要复杂企业流程。

#### 开源与独立开发者

- 希望工具可审计、可扩展且数据格式开放；
- 可能贡献功能、主题、导入器或插件。

### 2. 主要痛点

- 任务列表看不到时间关系和依赖带来的整体影响；
- 甘特图工具昂贵、笨重或必须联网；
- 项目计划调整后，需要在多个表格和图表中重复维护；
- 数据被封闭格式或云平台锁定；
- 轻量工具缺少依赖、里程碑和导入导出，专业工具又过于复杂。

### 3. 核心用户故事

- 作为项目负责人，我希望建立项目和任务层级，以便把目标拆成可执行工作；
- 作为项目成员，我希望看到任务时间、依赖和进度，以便明确下一步工作；
- 作为计划制定者，我希望拖动甘特图任务条即可调整时间，以便快速响应变化；
- 作为数据所有者，我希望导入和导出开放格式，以便备份、迁移和二次分析；
- 作为离线用户，我希望不登录也能使用全部核心功能，以便随时管理项目。

## 四、功能设计

### 1. 核心业务闭环

1. 创建项目；
2. 新建或导入任务；
3. 设置任务层级、时间、依赖、负责人和优先级；
4. 在任务表与甘特图中检查计划；
5. 在看板中按状态推进任务；
6. 执行过程中更新状态、进度与时间；
7. 识别逾期、冲突和依赖风险；
8. 导出、归档或复用项目模板。

### 2. 项目管理

- 项目字段：名称、描述、版本、状态、负责人、计划起止时间、创建/更新时间；
- 项目状态：草稿、进行中、已暂停、已完成、已归档；
- 删除默认采用软删除，并提供恢复入口；
- 项目列表支持搜索、状态筛选和最近更新时间排序。

### 3. 任务管理

- 任务字段：名称、所属项目、父任务、类型、状态、优先级、进度、负责人、起止时间、备注；
- 任务类型：普通任务、摘要任务、里程碑；
- 支持树形层级、拖动排序和批量编辑；
- 结束时间不得早于开始时间；
- 进度范围为 0–100%；
- 完成任务时默认将进度设置为 100%，用户可撤销；
- 父任务时间和进度可根据子任务汇总，具体规则在实现前固定。

### 4. 依赖管理

- MVP 首先支持“完成后开始（FS）”依赖；
- 禁止任务依赖自身；
- 禁止形成循环依赖；
- 删除任务前提示其子任务和依赖关系影响；
- 后续可扩展 SS、FF、SF 以及提前量/延迟量。

### 5. 甘特图

- 左侧任务树，右侧时间轴；
- 展示任务条、里程碑、进度和依赖线；
- 支持日、周、月缩放和跳转到今天；
- 拖动任务条调整时间，拖动端点调整工期；
- 修改后同步更新任务表和数据库；
- 对逾期、时间冲突、无效依赖进行视觉提示；
- 大数据量采用虚拟滚动或可见区域渲染。

### 6. 导入导出

- JSON：完整保留项目、任务层级、依赖和元数据，作为原生交换格式；
- CSV：用于通用表格交换，通过稳定 ID 表达父子和依赖关系；
- XLSX：按领域模型拆分工作表，支持列名映射、计数预览与 Excel 编辑；
- ICS：导出项目排期，并将外部文件或私有订阅中的忙碌事件写入成员不可用日期；
- 导入流程包含文件解析、字段映射、数据预览、校验报告和最终确认；
- 导入操作应使用数据库事务，失败时完整回滚；
- 导出格式包含 `schemaVersion`；当前为 v5，完整交换 Project、Task、Member、ProjectMember、TaskDependency 与 PlanBaseline，并兼容导入 v1–v5。
- JSON 导入先校验模型关系并在事务中替换数据，失败时保持原工作区不变；SQLite 恢复仅接受应用备份目录内经过完整性校验的 `.db` 文件，并先创建安全快照。

原始功能清单：[Wolai 页面](https://www.wolai.com/27YK2TtKiktYrg9ovqkTa6)。在公开页面内容可读取后，应逐项映射到 P0/P1/P2，避免功能遗漏或范围膨胀。

## 五、技术方案

### 1. 本地桌面 MVP

- 前端：Vue 3 + Vite；
- UI：PrimeVue，建立统一主题和设计变量；
- 桌面容器：Tauri 2；
- 本地服务：Rust Tauri Commands；
- 数据库：SQLite；
- 测试：Rust 单元/集成测试 + 前端组件测试 + 核心流程端到端测试。

### 2. 推荐模块划分

#### 前端

- `modules/project`：项目列表、项目表单；
- `modules/task`：任务树、任务编辑和筛选；
- `modules/gantt`：时间轴、任务条、依赖线和交互；
- `modules/import-export`：解析、校验、预览和导出；
- `services`：统一封装 Tauri 调用和错误处理；
- `shared`：通用组件、类型、常量和工具函数。

#### Rust

- `commands`：稳定、明确的前端调用入口；
- `services`：业务规则和事务编排；
- `repositories`：SQLite 查询与持久化；
- `models`：数据库模型、请求 DTO 和响应 DTO；
- `migrations`：数据库版本迁移；
- `import_export`：文件格式和版本兼容。

模型划分参考：[Wolai 页面](https://www.wolai.com/asmUaheAc1VN5b2uKnxW7h)。

### 3. 前后端交互规范

- 避免继续扩展通用的 `crud_action(model, action, data)`；
- 新功能采用明确命令，如 `create_project`、`update_task`、`list_tasks`；
- 每个命令使用强类型请求 DTO，禁止将任意 JSON 字段拼入 SQL；
- 更新操作使用字段白名单，系统字段不可由前端覆盖；
- 响应统一包含成功数据或结构化错误码；
- 列表接口统一分页、筛选和排序参数；
- 批量导入、批量移动和级联删除使用事务。

### 4. 数据库设计建议

#### Project

- `id`：稳定唯一标识；
- `name`、`description`、`version`；
- `status`、`owner`；
- `planned_start_at`、`planned_end_at`；
- `created_at`、`updated_at`、`deleted_at`。

#### Task

- `id`、`project_id`、`parent_id`；
- `name`、`description`、`type`；
- `status`、`priority`、`progress`；
- `assignee`；
- `planned_start_at`、`planned_end_at`；
- `sort_order`；
- `created_at`、`updated_at`、`deleted_at`。

#### TaskDependency

- `id`；
- `predecessor_task_id`；
- `successor_task_id`；
- `dependency_type`；
- `lag_minutes`；
- 唯一约束与禁止自依赖约束。

依赖关系不建议继续用逗号分隔字符串存储，应独立建表，以支持完整性校验、查询和后续扩展。

数据库设计参考：[Wolai 页面](https://www.wolai.com/mH3j99ZvMqoL6XKi4VtCCB)。

### 5. 本地数据与迁移

- 数据库文件放在 Tauri 提供的应用数据目录，不依赖启动工作目录；
- 首次启动执行初始化；数据库使用 `PRAGMA user_version` 标记当前 schema v5，拒绝打开高于应用支持版本的数据文件；
- 迁移前自动备份；
- 开启外键约束，并为 `project_id`、`parent_id`、状态和排序字段建立必要索引；
- 升级时自动补齐“项目负责人/任务负责人必须属于项目团队”的历史关系；新建与编辑任务时强制校验有效成员和项目团队关系；
- 日期在数据库中使用统一格式，界面负责本地时区展示；
- 数据导出格式与数据库结构解耦。

### 6. 桌面安全边界

- WebView 使用显式 CSP，只允许应用自身资源、Tauri IPC 和必要的本地资源协议；
- 在线 ICS 仅允许 HTTP/HTTPS，拒绝凭据内嵌、localhost、回环/私网/链路本地地址，并对重定向目标重复校验；
- 备份恢复只允许应用管理的备份目录，避免任意本地数据库路径被替换；
- 生产日志默认 `warn`，业务日志不记录完整项目、任务或 SQL 参数；
- 文件打开权限限制在应用数据目录；公开发行前仍需完成 Windows/macOS 签名与各平台人工冒烟测试。

### 7. 多端未来版

只有在桌面 MVP 获得真实使用验证后再启动多端版本：

- Web：复用 Vue 业务层与组件，适配浏览器存储和服务端 API；
- 桌面：Tauri + SQLite 缓存；
- 移动：优先评估 Capacitor 复用成本，再决定是否采用 Flutter；
- 服务端：Rust Axum/Actix 或 Java Spring Boot；
- 云数据库：优先 PostgreSQL；
- 同步：基于实体版本、更新时间、删除标记和操作日志设计冲突策略。

不要把“SQLite 与云数据库互传”视为简单复制；账号体系、离线队列、幂等、冲突合并和数据迁移必须先独立设计。

## 六、界面与体验

### 1. 信息架构

- 一级导航：Dashboard、Projects、Tasks、Data；甘特图不是独立一级页面；
- 首页：项目指标、近期任务和快捷入口，任务必须同时展示所属项目；
- Projects：项目列表；点击项目名称进入对应项目详情；
- 项目工作区：共享同一 `project_id` 的任务表 / 甘特图双视图，通过详情页内分段按钮切换；

- 导入导出中心：预览、校验和历史记录；
- 设置：主题、日期格式、数据目录、备份与恢复。

### 2. 交互原则

- 主要操作在当前上下文完成，减少多层弹窗；
- 所有异步操作提供加载、成功和失败反馈；
- 删除、覆盖导入等高风险操作必须明确影响范围；
- 表格编辑失败时保留用户输入，允许重试；
- 颜色不是状态的唯一表达方式；
- 键盘操作覆盖新建、保存、取消、搜索和任务移动等高频行为。

界面原型：[Mockplus 页面](https://rp.mockplus.cn/team/ps3589282)。正式开发前应将原型页面逐一映射到用户故事和验收标准。

## 八、风险与应对

| 风险                     | 影响                       | 应对策略                                    |
| ------------------------ | -------------------------- | ------------------------------------------- |
| MVP 功能持续膨胀         | 延期且核心体验不完整       | 严格执行 P0/P1/P2，新增需求必须替换而非叠加 |
| 甘特图交互复杂、性能不足 | 核心功能不可用             | 在 M1 前制作技术原型，用 1000 个任务压测    |
| 前后端模型不一致         | 新增、编辑失败或数据丢失   | 单一领域模型、强类型 DTO、契约测试          |
| 依赖关系用字符串存储     | 无法校验循环依赖，查询困难 | 使用独立依赖表和事务校验                    |
| 数据库路径与升级不稳定   | 发布后数据丢失或无法启动   | 应用数据目录、版本迁移、迁移前备份          |
| 导入文件污染现有数据     | 数据损坏                   | 预览、严格校验、事务、导入前自动备份        |
| 多端同步过早设计         | 架构复杂度拖垮 MVP         | 桌面闭环验证后再设计同步协议                |
| 开源项目缺少持续维护     | 用户信任下降               | 明确路线图、贡献指南、Issue 模板和发布节奏  |
