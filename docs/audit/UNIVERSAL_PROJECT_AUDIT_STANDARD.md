# 通用项目审计与整改标准（UPARS）

- 标准编号：UPARS
- 版本：1.1.0
- 状态：正式
- 适用范围：所有软件项目；与项目仓库内的审计补充规则配合使用
- 配套文件：`config/audit/audit-standard.json`、`docs/audit/AUDIT_REPORT_TEMPLATE.md`

## 1. 目标

UPARS 用统一、可追溯、可验证的方式回答四个问题：

1. 审计检查了什么，明确排除了什么？
2. 发现的问题如何触发、影响什么、是否可进入发布路径？
3. 问题是否已整改，整改是否经过与风险相称的验证？
4. 项目现在能否进入下一发布阶段，仍有哪些例外或未知？

本标准同时适用于只读审计和“审计并整改”。任务未明确授权修改时，只能生成发现和建议；获得整改授权后，必须闭环到验证结果，不能把“已发现”写成“已完成”。

## 2. 规范用语

- **必须**：缺失即不符合本标准。
- **应该**：原则上执行；不执行时必须记录原因和替代控制。
- **可以**：按项目风险和技术栈选择。
- **门禁**：可重复执行、失败会阻止合入或发布的检查。
- **确认问题**：具备充分证据和明确影响的 finding。
- **未知**：证据不足，既不能判定安全也不能判定存在缺陷。
- **例外**：经明确理由、责任人和复查条件批准的偏离。

## 3. 审计输入与基线

审计开始前必须记录：

- 项目名称、版本、仓库/工作区位置与提交基线；
- 审计模式：只读，或审计并整改；
- 发布目标、运行平台、支持版本与主要用户路径；
- 语言、框架、构建系统、数据存储、外部服务和凭据边界；
- 已有测试、CI、静态检查、签名和部署机制；
- 用户明确授权的外部写入、设备操作和破坏性操作边界；
- 审计范围、排除项及排除理由。

工作区存在未提交修改时，审计必须将其视为用户资产；不得覆盖、回退或混入无关改动。

## 4. 必审域

每个项目都必须对以下域给出“已检查”“不适用”或“排除”的明确结论。仅列工具输出而没有人工判断，不构成完整审计。

### 4.1 编码规范与可维护性

编码规范是独立的必审域，报告不得省略。至少检查：

- 格式、缩进、换行、命名、导入和文件组织；
- 控制流大括号、空块、重复声明、死代码和未使用资源；
- 方法/函数长度、圈复杂度、NPath 或同类复杂度指标；
- 类型检查、空值边界、错误处理和日志质量；
- 语言官方格式器及主流 Lint 是否存在、是否进入 CI；
- 规则豁免是否局部、必要、有理由且可复查。

新项目必须建立零错误门禁。警告默认也必须清零；确属工具误报或平台约束时，可使用最窄范围的有理由豁免，并在报告中登记。

### 4.2 正确性与可靠性

- 主流程、异常流程、取消、重试、恢复和幂等；
- 输入边界、状态转换、生命周期、并发、竞态和资源释放；
- 超时、失败回滚、部分成功和断电/进程终止恢复；
- 错误是否被吞掉、误报成功或覆盖真实根因。

### 4.3 安全与隐私

- 身份认证、授权、最小权限和组件导出边界；
- 路径穿越、命令注入、XML/ZIP/反序列化、容量耗尽等输入风险；
- 凭据、令牌、密钥、隐私数据的存储、日志和传输；
- 网络访问是否默认安全，在线处理是否需要明确同意；
- 当外部地址经解析、跳转或代理后用于连接时，必须检查校验与实际使用是否绑定；通过条件是每次连接均使用已校验目标或等价的强制策略，验证须覆盖目标变化的反例；
- 外部进程、脚本、临时目录和文件权限边界；
- 依赖来源、锁定、已知风险和供应链控制。

### 4.4 数据与存储

- 数据模型、迁移、事务、唯一性、外键和一致性；
- 导入/导出、校验和、原子提交、备份和恢复；
- 缓存、断点和临时文件是否可安全清理；
- 删除、覆盖和迁移是否可逆，是否保留用户数据。

### 4.5 UI、无障碍与国际化

- 目标屏幕、缩放、主题、旋转和输入方式；
- 触摸目标、键盘/表冠/辅助功能语义及焦点顺序；
- 文案、错误反馈、加载/空/完成状态；
- 多语言、Unicode、长文本、RTL（适用时）和格式化。

### 4.6 构建、测试与发布

- 可复现构建、锁文件、编译警告和发布优化；
- 单元、集成、端到端、设备或平台测试的覆盖与隔离；
- Debug/Test/Release 产物、签名身份和配置差异；
- CI 是否覆盖实际语言、源集和发布路径；
- 文档、版本号、变更记录和运维/回滚说明是否同步。

## 5. 发现记录格式

每个确认问题必须有稳定 ID，并至少包含：

| 字段       | 要求                                          |
| ---------- | --------------------------------------------- |
| ID         | 项目内稳定且唯一；推荐 `<项目>-<域>-NNN`      |
| 状态       | `open`、`fixed`、`accepted`、`not_applicable` |
| 严重度     | P0、P1、P2 或 P3                              |
| 置信度     | 高、中或低                                    |
| 范围       | 组件、文件、接口或用户路径                    |
| 证据       | 可复核的代码位置、命令结果、日志或测试        |
| 触发条件   | 问题出现所需的输入、状态或环境                |
| 影响       | 对安全、数据、功能、用户或维护的实际后果      |
| 发布可达性 | 当前发布产物是否能触达；不能时说明原因        |
| 整改       | 实际完成的控制；未整改时写建议或接受理由      |
| 验证       | 验证命令、测试、构建及结果；不能只写“已测试”  |
| 责任与复查 | accepted/未知项必须记录责任人或复查条件       |

多个工具对同一根因的重复报错应合并为一个 finding，并保留数量统计。单纯缺少证据的事项应记录为未知，不能伪装成低严重度确认问题。

## 6. 严重度

| 级别 | 定义                                                                | 默认发布处理                           |
| ---- | ------------------------------------------------------------------- | -------------------------------------- |
| P0   | 已发生或极易触发的灾难性安全、隐私、数据破坏或核心不可用            | 立即阻断；不得发布                     |
| P1   | 可从支持路径触达的高影响安全、数据丢失、持续崩溃或关键功能失效      | 必须整改并复验；不得带入发布           |
| P2   | 有实际影响的边界缺陷、可靠性/无障碍问题、显著维护风险或关键门禁缺失 | 应在本轮关闭；接受例外需明确责任与期限 |
| P3   | 低影响质量债、工具环境缺口、局部一致性或体验问题                    | 记录并排期；不得隐瞒为“无问题”         |

严重度由“影响 × 可触达性 × 发生概率”综合决定；置信度单独记录，不能用低置信度替代严重度。

## 7. 审计并整改闭环

获得整改授权后，每个确认问题必须依次完成：

1. 固定基线并保存原始证据；
2. 确定根因、影响面和发布可达性；
3. 采用范围最小且可维护的整改；
4. 增加或更新能证明根因已关闭的测试/门禁；
5. 运行与风险相称的回归；
6. 更新 finding 状态、验证证据、文档与 CI；
7. 复查差异，确认没有临时工具、凭据、构建产物或无关改动进入交付。

禁止仅通过扩大忽略范围、关闭规则、吞掉异常或降低阈值来“清零”。确需豁免时，必须证明行为正确且豁免范围最窄。

## 8. 技术栈最低门禁

项目只需执行适用项，但必须在报告中列出未适用项。

| 技术栈                          | 最低门禁                                                                                                   |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Java/Kotlin/Android             | 格式/Checkstyle 或同等 Lint、复杂度、单元测试、Android Lint、Debug 构建；发布前增加 Release 构建与签名核验 |
| JavaScript/TypeScript/Vue/React | 锁定依赖、ESLint、类型检查、单元测试（存在业务逻辑时）、生产构建                                           |
| Rust                            | `cargo fmt --check`、Clippy 且 warning 视为错误、`cargo test`、目标平台构建                                |
| Python                          | Ruff 或同类格式/Lint、语法编译、类型检查（适用时）、pytest 或同类测试                                      |
| PowerShell                      | AST 语法解析、PSScriptAnalyzer（可用时）、正负例测试；危险文件操作需验证目标边界                           |
| 数据库                          | Schema/迁移测试、事务与回滚、约束、升级/降级或恢复策略                                                     |
| 网络/API                        | 输入输出契约、超时重试、证书/传输、鉴权、速率限制、隐私同意与日志脱敏                                      |

仓库可增加更严格规则，不得低于本表而不记录例外。

## 9. 发布判定

只有同时满足以下条件，报告才可判定“代码层审计通过”：

- 所有必审域有结论，范围和排除项明确；
- P0/P1 未关闭数为 0；
- P2 已关闭，或具有经批准的责任人、期限和替代控制；
- 强制规范、测试、构建和安全门禁全部通过；
- 警告为 0，或每一项都有局部、可复查的例外；
- 设备、账号、在线服务或发布签名未验证时，明确写为例外/未知；
- 报告包含基线、证据、整改和最终验证，不把历史结果冒充当前结果。

“代码层审计通过”不自动等于“可正式发布”。真实设备、生产账号、正式签名、安装包、迁移和回滚等发布验收必须单独判定。

## 10. 交付物

每次审计至少交付：

1. 按模板生成的审计报告；
2. finding 清单及状态；
3. 规范/测试/构建/安全门禁结果摘要；
4. 实际整改差异；
5. 排除项、未知、设备例外和发布判定；
6. 新增或更新的持续门禁。

报告模板位于 `docs/audit/AUDIT_REPORT_TEMPLATE.md`。机器可读的域、字段、严重度和发布规则位于 `config/audit/audit-standard.json`，二者必须保持同一版本。

## 11. 项目接入清单

新项目接入时必须：

- 在项目 README 声明采用的 UPARS 版本；
- 列出技术栈和对应的最低门禁命令；
- 将规范、测试、生产构建和适用安全门禁接入 CI；
- 使用稳定 finding ID 和统一报告模板；
- 声明项目特有的敏感数据、外部服务、设备及发布签名边界；
- 完成至少一个安全门禁正例和一个负例，证明门禁既不误拦也不漏拦；
- 标准升级时记录差异，并重新评估新增必审域或发布条件。

## 12. 项目补充规则

平台、产品和业务特有要求必须放在项目仓库自己的审计 profile 中。项目 profile：

- 必须声明采用的 UPARS 版本、适用项目和技术栈；
- 应列出项目专属风险、门禁命令、设备/服务边界和发布验收项；
- 可以增加或收紧要求，不得静默降低 UPARS 的必审域、严重度或发布门槛；
- 确需偏离时，必须按例外登记责任人、原因、期限和替代控制；
- 不得复制整份 UPARS，避免全局标准与项目副本发生漂移。

## 13. 标准补充规则

审计发现标准未覆盖的内容时，先处理当前项目风险，再判断其是否具有跨项目复用价值。补充到 UPARS 的要求必须：

- 技术栈中立，或清楚标明适用条件；
- 说明风险、检查方法、通过条件和验证方式；
- 不包含单一产品的业务规则、文件路径或临时事故细节；
- 经用户授权后修改，并同步更新标准、模板和机器规则；
- 通过 `scripts/verify-audit-standard.ps1` 校验。

仅适用于某一项目的内容应补充到项目 profile，不应进入 UPARS。

## 14. 版本治理

- 修订错字或不改变要求：补丁版本。
- 新增兼容的字段、域或建议：次版本。
- 改变严重度、必审域或发布条件：主版本。
- 标准文件和机器配置的版本必须同步；审计报告必须写明采用的版本。
